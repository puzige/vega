## Authority and product boundary

- Vega follows the open [Agent Skills format specification](https://agentskills.io/specification) for `SKILL.md` packaging and its [client integration guide](https://agentskills.io/client-implementation/adding-skills-support) for three-tier disclosure. The format specifies files, not a mandatory home directory or permission model. The Issue's image is a reference only, not instructions.
- A Skill is **workflow guidance and optional resources**, not a tool, plugin sandbox, permission grant, credential source, or new user request. Model instructions in it may guide use of capabilities already available to this thread, but cannot override Vega's run mode, tool approval, dangerous-command check, path fence, OS sandbox, stop/cancel, or MCP authorization. The experimental `allowed-tools` frontmatter field is parsed only for display/diagnostics and grants **zero** authority.
- This card includes local discovery, UI trust/management, explicit and model-driven activation, progressive loading of references/assets, a visible activation record, restart-safe selection, and production wiring. It excludes remote installation/marketplace, WASI, plugin APIs, arbitrary home scanning, subagent dispatch, special script privileges, and new MCP servers. #73 owns MCP client/tool authority; #76 owns model context-budget policy.

## S1 · Sources, identity and trust

1. Scan only these exact one-level roots: selected project's `<canonical-project>/.agents/skills`, and Vega-owned `<vega_store::paths::config_dir()>/skills`. The existing `config_dir()` resolver is the sole platform/environment authority; do not reconstruct a home/XDG path independently. A candidate is `<root>/<name>/SKILL.md`; no recursive home search or ancestor walk. Project discovery is conditional on that exact project's Skills consent. Vega-owned global files are visible in Settings but not model-enabled until individually approved.
2. Additional global roots (for example `~/.agents/skills`, `~/.pi/agent/skills`, `~/.codex/skills`) are **not scanned by default**. The user may choose an exact directory in Vega Settings via a native folder picker, see its canonical target and source label, then authorize the association. Import-by-reference does not copy, modify, execute, or delete source files. Unlinking removes Vega's association/consent only; original files remain. Do not follow neighbouring directories or infer authorization for a different client from its mere presence.
3. A skill identity is `(scope, canonical root identity, validated name)` plus the content SHA-256 used for consent and run snapshots. Canonical root and source label are shown in Settings; provider prompts and public traces use a stable opaque source label rather than exposing private absolute paths. Duplicate canonical imports are collapsed, not counted twice.
4. For the **automatic model catalog**, among enabled and hash-approved candidates of the same name choose: exact project > Vega-owned global > external imported roots in explicit UI order (earlier priority first; ties by canonical path bytes). An unapproved/disabled project candidate cannot shadow an approved global candidate. Settings shows all shadowed candidates and the winner; an explicit UI picker may select an approved shadowed source by full identity. Never silently fall back to a different copy after the selected one disappears or fails validation.
5. Project and global consent are distinct. First project activation requires UI preview/approval for the canonical project and selected Skill hash; global and imported candidates require the same per-Skill preview/approval. **Global and automatic use start disabled as a safety default, not as a missing feature**: the user can discover/import, consent to, enable, and use both fully through Vega's UI. UI can enable/disable auto activation globally, per project, and per Skill; disable/unlink acts before the next run, and revocation during a run cancels that run rather than silently continuing with instructions the user revoked. Consent state is persisted through the conversation/store service, never by asking the user to hand-edit TOML/SQLite.
6. A source file changed since consent is visibly `changed—review required` for **new** runs, including a branch switch. A running request keeps its frozen approved Skill body and hash across retries and tool rounds. New bytes never silently inherit old consent. Missing, malformed, stale, or unsafe candidates are skipped from the model catalog with a bounded UI diagnostic, not replaced by a shadowed source without selection.

## S2 · Format, discovery and filesystem boundary

- `SKILL.md` requires YAML frontmatter and Markdown body. Enforce the official required `name`/`description` constraints, including directory-name match; accept official optional `license`, `compatibility`, `metadata`, and `allowed-tools` syntactically. Unknown keys may be retained for display but have no Vega behavior. Unlike the client guide's optional lenient repair, Vega does **not** silently rewrite malformed YAML or infer a missing description: surface a diagnostic and keep that candidate disabled. Full YAML support needs an architect-approved parser dependency; do not claim strict format compatibility from an ad-hoc partial parser. The frontmatter must be one mapping document; reject duplicate keys, unexpected document boundaries and parser extensions that read files or interpolate environment values.
- Read only bounded metadata during discovery. Proposed hard ceilings (reviewable): 8 KiB frontmatter, 128 KiB `SKILL.md`, 128 discoverable candidates per root, and 128 KiB serialized model catalog. A limit failure is visible, never silently truncated into a different instruction. The official `<5000 token` / `<500 line` guidance is a warning, not Vega's validity test. Limits apply to UTF-8 bytes and are independently tested.
- Discovery uses `lstat`/canonical resolution for the approved root and candidate; before **every activation/resource load** re-resolve from the approved root, recheck each path segment, regular-file type, size, canonical containment, and approved hash. Reject `..`, absolute paths, path-component escapes, outside-root symlinks and multi-linked files. A UI-imported root that itself resolves through a symlink is shown and approved by its canonical target; retargeting it revokes association. Do not trust a path recorded at discovery as authority at load time. Use descriptor/no-follow checks where supported to narrow TOCTOU, and return a typed unsafe/stale error rather than content when identity changes between check and read.
- Discovery never reads script bodies, `references/`, or `assets/`. Do not traverse arbitrary nested directories; resource paths are resolved relative to the activated canonical Skill root with the same fence. **Approval of `SKILL.md` is not approval of a reference's bytes.** At the first on-demand resource read, validate the current root/path, regular-file type, size and content hash, label returned text as lower-trust, and freeze its exact hash/bytes in that run snapshot; subsequent reads in the same run return that snapshot, never newly changed external bytes. Text resources have bounded UTF-8/binary checks (32 KiB each, 128 KiB and 128 distinct references per run). Binary assets are listed by validated relative path/type/size (type may be unknown), not injected as text or automatically uploaded. No resource may claim a new root, permission, or tool. The UI may offer a preview before first read, but it must not imply that unseen reference contents were pre-approved.

## S3 · Progressive disclosure and automatic activation

1. At a user-submitted turn, freeze the enabled, approved, deduplicated catalog. The provider sees only each available Skill's `name`, `description` and opaque source label, not all bodies. If empty, inject no Skills section and advertise no Skill tools. Catalog bytes enter #76 input estimation. Do not include disabled/unconsented candidates or a private absolute path. This is tier 1 of the official format.
2. A user may select an approved Skill in a native picker before send. The selection binds its full identity/hash to the thread and survives restart until unpinned/disabled. Explicit selection loads the body before the first provider request. A user-submitted new turn may also let the model decide semantic relevance from the catalog: the system rule is to call the reserved read-only `load_skill` tool **before other task tools** when the latest user task matches a description. No brittle keyword matching or activation from web pages, tool results, screenshots, or historical summaries. The model may select none; automatic triggering is a model decision, not a guarantee from a text heuristic.
3. The host-side trigger state machine is deterministic and testable: accept `load_skill({"name":"<catalog-name>"})` only for a current direct-user run, an exact name in its frozen enabled catalog, valid unchanged consent, and at most three distinct activations per run (proposed cap). Reject unknown/disabled/stale/duplicate/over-cap calls with bounded stable results and zero file access on the invalid path. If an assistant batch includes `load_skill` and any operational tool, resolve the Skill call and **reject all other calls in that batch without execution**; the model may propose them again after seeing the loaded instructions. A batch of only `load_skill` calls is processed serially. No model-proposed path or arbitrary source ID is accepted.
4. An accepted `load_skill` call produces a content-free tool receipt and a typed activation audit (run/thread, name, source scope, content hash, user/model origin, success/failure, no body/path). Its bounded, hash-frozen body is installed into a labelled Skill section of the next and all later provider **system envelopes** for that run; no duplicate body in ordinary tool-result history. Base Vega safety instructions explicitly subordinate Skill content to user intent, mode and permission decisions. The active section is rebuilt after #76 compaction, never summarized as historical data. Repeated load attempts do not duplicate instruction text or charge it twice in one request.
5. The run snapshot includes exact body bytes/hash and activation order. Persist a bounded local snapshot so a process restart can validate and display the interrupted run's frozen provenance without reading modified external files. Vega's existing startup recovery marks an incomplete assistant run `interrupted` and cancels unfinished tools; it **does not automatically resume that run or replay any provider/tool side effect**. A later user submission/retry creates a new run and rechecks current consent and source hashes. The trusted Store must retain a separate `RunBinding` (run ID, thread ID, consent generation, revocation generation, frozen catalog SHA-256) **and the whole-snapshot SHA-256** in trusted run metadata and pass both to read-only recovery; hashes stored only beside their own bytes are not an integrity check. Recovery compares that binding and digest, version, size, catalog shape/hash, active body bytes/hash/order, and first-read reference bytes/hash/path before returning validated provenance, without rereading activated content from disk. This is application persistence integrity, not protection against a malicious local process that can rewrite both snapshot and trusted metadata. Unactivated candidates are still subject to the ordinary live path/hash fence on a new run. The 1 MiB JSON snapshot limit and its exact representation are private Store/runtime details, not a public wire or Skill format. A thread pin stores identity/hash but does not silently adopt changed content on a **new** run. Snapshot content is local private data, not a public Issue/log attachment; its retention follows thread deletion. Revocation stops an active run, leaves the assistant row `interrupted`, and writes an idempotent content-free `revoked` audit for each activated Skill; a changed consent epoch is conservatively cancelled because this run can no longer advance its durable snapshot. The UI shows which Skill was auto-selected, source, and `Stop` / `Disable future activation`; it must explain that stopping cannot undo actions already completed, while `load_skill` itself has no side effects.
6. Tier 3 resources use a reserved read-only `read_skill_resource({"name":"...","path":"references/..."})` or equivalent shared registry operation, only after that exact Skill is activated. Return bounded text plus type/hash, not a raw unrestricted filesystem handle. Assets remain optional input to existing tools only if separately selected and allowed. Deduplicate repeated resource reads in one run; check the actual returned bytes in #76's next-request estimate.

## S4 · Script execution and tool authority

- No dedicated `run_skill` shortcut, shell bypass, ambient `allowed-tools` permission, automatic script execution on activation, or config mutation. A script referenced by an activated Skill is **data until the agent proposes an existing tool call**. Project scripts may be invoked through current project-root `bash` only in Execute mode; Ask/Plan, ReadOnly, Confirm, Auto and FullAccess retain their existing exact permission, dangerous-command, sandbox and cancellation behavior. The user must see the real command/target in the existing approval/audit path.
- Global scripts outside the selected project are not copied into the project or given write/sandbox exceptions. If the current `bash` sandbox cannot access them, the operation is unavailable with an honest error; the user may choose FullAccess only through Vega's existing explicit mode UI, never because a Skill asks. Reading a global reference via `read_skill_resource` does not grant its script execute permission. Skill import/enable consent authorizes **instruction availability**, not script/MCP execution.
- The Skill body, metadata, resource text, asset contents, tool results and attached Issue screenshot are lower-trust content. They cannot mint a permission rule, change `run_mode`, request hidden credentials, add a provider tool, or bypass #73 MCP consent. Runtime guards, not prompt wording alone, are the authority. Do not persist raw Skill/script contents in tool audit, tracing, public evidence or errors.

## S5 · UI and durable state

- Add Settings → Skills using existing Vega theme tokens: source roots with exact provenance and unlink action, candidate list including shadowed/invalid/changed states, bounded preview, per-root/per-Skill enable and automatic toggle, refresh, and an explicit native UI import of an external root. No fake marketplace/install status. The model sees only enabled/consented winners.
- The Composer/active task shows a compact source-labelled active Skill indicator and an explicit picker/pin control without moving #76 model capacity controls back into the Composer. Confirm/disable/revoke/stop are handled through UI controller services, not direct UI SQLite reads. First-use/project-trust consent must explain that repository files are instructions and may contain scripts, but **not** imply permission to execute them.
- For an R69 new-task draft, explicit selection is only a UI intent: opening the picker or selecting a row must not materialize the thread. On first send, provider readiness completes first, then the existing draft is materialized under its final ID; a background controller rechecks the exact source/root/body SHA and approval and transactionally pins with the current consent generation before the Agent Loop starts. A failed or stale pin preserves the composer input and retryable intent, sends no provider request, and executes no Skill. Repeated clicks/sends cannot create duplicate pins or requests. A normal no-Skill draft keeps the existing R69 first-send path.
- Persist root associations and per-Skill consent/enable/hash separately from provider credentials, and thread pins/activation audits in conversation-owned storage with additive migrations. The source's canonical identity is stable across restarts; if its path/file has changed, mark review-required rather than reusing old approval. Do not edit an installed migration or choose a migration number before #76/#73 integration determines the next free number. Keep UI-only edits atomic and durable; last-write/late-result fencing prevents a stale background scan from re-enabling revoked content.

### Store 0013 additive contract (reserved after #76 0011 and #73 0012)

The frozen product decisions above require seven private, additive tables: a singleton `skill_settings` with global enable/automatic defaults **off** and monotonic consent/revocation generations; `skill_project_settings` with per-project enable/automatic defaults off; `skill_sources` with UI-minted opaque source ID, scope, optional project ID, configured path, canonical path/device/inode, import order, and per-root enable/automatic flags; `skill_approvals` with source ID, validated name, exact approved SHA-256, source label, enable/automatic flags; `thread_skill_pins` with full source identity/name/hash so a missing root remains visibly pinned but unavailable rather than silently substituted; `skill_run_snapshots` with bounded private bytes, separately stored full digest, run/thread/catalog/epoch binding; and `skill_activation_audits` with only run/thread, name, scope, content hash, origin/status/time (no body, resource bytes, or private path). Thread-owned rows cascade on thread deletion; unlinking a source removes its Vega association and approval rows, never files on disk.

Only the conversation/controller may write these rows after UI actions. One transaction applies each consent mutation and increments the global consent generation; disabling or unlinking also increments the revocation generation. Store API does not grant file trust by itself: the controller must preview/validate a `SkillSource` and candidate through the runtime fence before writing approval, compare current generations on resume, and cancel a live run on revocation. A source path is stored for later re-binding, not proof that the directory still exists or is safe. Store snapshot load validates its independently persisted SHA and bounded length; the runtime then validates `RunBinding`, catalog and frozen content. This schema is independent of #73's MCP tables. The port branch based on #73 checkpoint `5c37434` registers 0013 after 0011/0012 and tests the production v12→v13 upgrade, existing MCP/thread preservation and foreign-key integrity.

The staged controller bridge must reconstruct an old approval with `SkillApproval::from_persisted_parts` using the stored scope/canonical path/device/inode and **stored old SHA**; a newly discovered candidate does not mint approval for changed bytes. `RunBinding::from_trusted_parts` similarly accepts only separately stored run/thread/epoch/catalog fields. Both are internal trusted-controller APIs, not model-callable tools or a grant of file authority.

## Failure policy, acceptance and rollback

- Empty/missing root is a truthful empty catalog. Malformed/duplicate/unsafe candidates are visible but unavailable. Backend or UI scan failure does not reuse a stale catalog as if current. If a pinned or selected Skill is unavailable, pause the run before a provider or operational tool call and surface the exact safe failure class; never silently substitute another source. Auto-selection failure may return a rejected receipt and continue without that Skill only when no explicit/pinned selection depended on it.
- [The test-first matrix](vega-issue-74-skills-delivery.md) is normative. At minimum S01–S19 must be protected by production-path tests and safety regressions; S20/S21 require installed native UI, real configured model, UI-only consent and persistent screenshots. #73-dependent rows cannot be claimed PASS before a real local MCP server/tool call; a mock-only path is not a real provider or MCP result. Run Vega's format, strict Clippy, full workspace tests, package and architecture checks under the shared Cargo lock. Record raw results and residuals per exec-guide §7.
- Rollback removes Skills registration/UI without deleting user skill files or raw conversation history. Additive audit/pin rows remain readable or ignored by older code; no source directories are removed by unlinking. Do not close #74 or set Project Done until master integration, native evidence, exact worktree/branch cleanup and Issue write-back are complete.

### YAML parser dependency review (approved choice, headless tests passed)

The existing `Cargo.lock` already contains `serde-saphyr 0.0.29` through `rust-i18n-support 4.2.1`. Its [published manifest](https://docs.rs/crate/serde-saphyr/0.0.29/source/Cargo.toml.orig) declares MIT OR Apache-2.0, edition 2024, `serde_core` plus optional deserialization dependencies (`granit-parser 0.0.7`, `num-traits`, `annotate-snippets`, `smallvec`, `encoding_rs_io`, `ahash`); the baseline lock also includes its default serialization dependencies (`base64`, `nohash-hasher`, `zmij`). The [0.0.29 documentation](https://docs.rs/crate/serde-saphyr/0.0.29) provides typed `from_str_with_options`, duplicate-key rejection by default and configurable parsing budgets. `!include`/filesystem resolution and property interpolation are separate, off-by-default features and must **not** be enabled for Skill frontmatter. Limitation: 0.0.x API/behavior is older than the maintained 1.x line; pinning this exact version avoids a lockfile update now but requires later vulnerability/compatibility review rather than an automatic upgrade. Cargo feature unification means a new `default-features = false` declaration cannot remove features already enabled transitively.

Alternative: [noyalib 0.0.45](https://docs.rs/crate/noyalib/0.0.45) is active, pure Rust, MIT OR Apache-2.0, Rust 1.86+, and advertises YAML 1.2 conformance and explicit parser budgets. Its [manifest](https://docs.rs/crate/noyalib/0.0.45/source/Cargo.toml.orig) has required `serde_core`, `indexmap`, `rustc-hash`, `hashbrown 0.17`, `libm`, `memchr` and `smallvec`; the lean `default-features = false, features = ["std"]` profile omits optional `itoa`, `ryu` and `serde_ignored`. Those required transitive packages already occur in Vega's lock, but **noyalib itself does not**. Limitations for this card: a new 0.0.x crate and fresh supply-chain/build review, larger parsing/editing surface than frontmatter needs, and the lean profile lacks its strict unknown-field helper (Vega would still validate its own typed fields). Do not infer safety solely from upstream's conformance or `unsafe` claims.

The user approved exactly `serde-saphyr = "=0.0.29"` on 2026-09-20 under exec-guide §3/§5/§6. This is a **new direct dependency declaration**, though the lockfile adds only direct `vega_runtime` edges, not a new parser package. The 2026-09-20 focused headless gate passed 22 Skills tests (including forbidden `!include`/`!env`, duplicate-key, path-fence, consent-hash, catalog-budget and model-activation API cases), `cargo fmt --check`, and strict `vega_runtime` Clippy; `cargo tree -e features -i serde-saphyr` showed only `default`, `deserialize` and `serialize`, no include/properties. Full production-path S05/UI acceptance and the remaining package/license gate are still open. Do not silently upgrade the 0.0.29 line or enable filesystem/environment parser extensions. The user-approved existing workspace `sha2 = "=0.10.9"` is directly used by `vega_runtime` for Skill content identity; its version is unchanged.

### Shared integrator handoff still required

The isolated `vega_runtime::skills` API contains discovery/parser fences, consent-hash filtering, a bounded model catalog, model/explicit activation, mixed-tool-batch classification, content-free receipts, in-memory frozen body/reference bytes, and a bounded, binding/digest-checked private run-snapshot export/restore API. It does **not** register a provider tool, persist consent or a snapshot, render a native UI, or dispatch MCP. The single shared integrator must keep the Store-owned `RunBinding` and whole-snapshot SHA-256 separately from snapshot bytes, recheck current consent/revocation generations before restore, and persist the exact tool-schema set and selected #76 model-budget policy with its own run metadata. Recovery must not adopt changed source files; a revoked active run cancels. Add production S09/S11/S12/S14/S18/S19 tests for real Agent Loop dispatch, Store restart after external file change, revocation, compaction/wire counting, and MCP permission separation before claiming those rows PASS.
