# 首条发送即时临时标题

## 契约

新草稿通过 provider 预检与发送权限校验并持久化为正式任务时，在同一事务内写入原始 composer 文本归一化后的前 40 个 Unicode 字符。正式任务首次进入顶部和侧边栏时已有临时标题；不等待引用解析、provider 实例构造、MCP 或模型响应。未通过预检/事务失败仍保持草稿，不写标题。

已有任务不因普通发送被提前改名。纯图片/空白文本沿用既有占位行为。后台 AI 命名继续运行；手动改名状态永远优先。准备阶段失败后已创建任务保留临时标题，重试首条消息仍可取得自动命名资格。

## 实现

复用 automatic_titles 的归一化算法。prepare_submission_permission 仅对本次新创建且空标题任务设置临时标题；store 写入保持 eligible，并以 auto_title_claim 标记这是提前写入的自动临时标题。pipeline 仅在首条用户消息已存在且无其他消息时，将空 eligible 标题或带提前标记的 eligible 标题转为 claimed。手动改名设置 manual，不能取得 claim；finish_auto_title 的精确 message claim 检查不变。无需 schema 变更、UI 乐观状态或同步 UI IO。

## 验证与回归

本地仅格式、差异与静态调用链检查；无本地构建/测试，不新增 Rust 测试。最终 head 交现有 required Actions（fmt、Clippy、Python 与 Rust 空集发现/执行），并独立审查事务与命名状态边界。

用户手测：
1. 新任务发送中文、多行、超过 40 字的文本：正式任务首次显示即使用归一化前缀，顶部和侧边栏一致。
2. MCP 慢启动以及准备失败：不回退未命名，失败提示不隐藏。
3. AI 命名成功替换临时标题；AI 失败保留临时标题。
4. AI 期间手动改名不被覆盖；后续消息不覆盖已有标题。
5. 发送预检拒绝不产生错误标题；纯图片沿用原行为。
6. 创建后准备失败，再发送首条有效消息仍可自动命名。
