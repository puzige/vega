## Concrete pinned-API scope gap

The retained body currently builds `PreparedBody` with rendered UTF-8 ranges, original-source spans, per-fragment links, code horizontal ranges and selection remapping during source-window eviction. `ThinkingBody::publish_body` / `slide_body` feed that mapping into `MessageCopy::publish_retained`; the GPUI selection document consumes the positioned fragments.

NSH 0.4 offers `View::selectable`, but the GPUI backend's cross-text selection is stored in private `selectable_view::Active` / `SelectionModel`. Its `selected_text` and key/copy path are private. `Interactive` offers no cross-text selection-range callback; `on_selection_change` is on the editable input host and reports input UTF-16 selection, not a selectable view's document range. Its built-in copy writes displayed text directly to the clipboard and cannot call the retained-source mapper or current permission/selection guard. Text replacement is reconciled by backend text-node/content identity, not the existing original-source spans. Therefore replacing the body with plain selectable NSH text would silently lose the required source-range selection continuity; a readonly editable input would lose structured Markdown/link/code-viewport semantics.

This blocks a faithful direct reuse of NSH's built-in cross-text selection, not proof that every possible custom NSH selection implementation is impossible. A complete body migration needs a separate, validated custom selection/hit-testing/scrolling renderer over the existing source projection using only public pinned APIs, or a parent/user decision about the upstream API boundary. No such replacement is claimed by this stage. Existing GPUI body and scrollbars remain explicitly unmigrated, including `render_stage_source`; they are not wrapped into NSH. `sticky_disclosure` is shared with the run-activity integration and remains unchanged here.
