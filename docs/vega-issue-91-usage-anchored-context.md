## Contract

### U1 — authoritative input baseline and exact scope

An accepted, completed ordinary provider call may establish a run-local baseline using normalized `usage.input` for the exact request sent. It covers the input prefix, system prompt, model, tool schemas and provider/reasoning identity of that call, **not** the response generated by it. Predict the next request as that baseline plus the deterministic estimate of newly appended content that actually goes on the wire. Output usage, cache-read/write usage, thinking usage and prior framing already covered by that input must not be blindly added. Newly retained assistant text/reasoning/tool calls and tool results are estimated exactly once as the tail. Nonretained reasoning is not a tail contribution. Multiple calls/fragments in one response must neither omit nor duplicate results.

Maintain explicit covered-prefix identity, not just a message count or approximate byte count. Prefix equality and frozen request identity must be checked before reuse. A change of covered content, system text, model, tool definitions or reasoning invalidates the baseline. Provider identity is fixed by the run; never share a baseline between runs/providers. Do not retain unbounded extra copies of a long history just to validate an anchor; prefer existing bounded structural identity or a content fingerprint with available dependencies. Checked arithmetic and existing image accounting apply. Invalid data must not make the estimate zero or bypass hard bounds.

### U2 — acceptance, fallback and normalization

Establish a baseline only after the normal stream is validly completed (End or normal ToolUse), has exactly one valid nonzero input usage, and is neither cancelled, errored, truncated nor protocol-invalid. Existing stream protocol rejection is unchanged. Missing/invalid usage invalidates that call's baseline and produces a labelled deterministic fallback. Never use a summary call's usage, accumulated session billing, or a partial failed stream as a primary baseline. Existing usage accounting remains unchanged.

The current OpenAI-compatible normalizer defines input as `prompt_tokens` (including cached input); cache fields are breakdowns and must not be added again. Any other supported adapter must be checked against the same normalized input contract. Do not change price accounting or invent wire fields. No new dependencies or database migrations.

### U3 — lifecycle, all budget paths, safe first turn

Use one accounting decision for ordinary auto-compaction/hard-limit preflight and applicable pre-skill budget paths; preserve tool authority, permissions and pair completeness. Keep trigger/target/reserve semantics unchanged. Invalidate after compaction/projection replacement or historical reconstruction; do not reuse a pre-compaction count for a new prefix. First request, manual compaction and reopened sessions have no proven run-local baseline and use a clearly labelled estimate. Existing database usage rows do not prove exact reconstructed input identity, so they are not imported as anchors. The next valid primary response establishes a fresh baseline.

Post-compaction budget checks remain safe estimates of the new projection, not the old usage value or summary-call usage. In particular, a long current user/tool suffix is not dropped or silently summarized to force success. Distinguish these paths in diagnostics so a failed target check is not misrepresented as a provider-confirmed context overflow. This card does not promise a retry policy or eliminate all genuine invalid_summary failures.

### U4 — observable, consistent decisions

Expose content-free accounting metadata through runtime events and conversation facade: source (`Estimated`/`UsageAnchored` or equivalents), provider input baseline when valid, incremental estimate, final predicted input, input budget, trigger/target, and enough run-local revision/coverage metadata to correlate a decision with the subsequent call. No prompts, credentials, tool args/results or reasoning text in logs/Debug. Request decision and UI live accounting must share the same value/source; a durable reloaded estimate must not silently overwrite an active anchored decision and claim to be measured. Reset live metadata at run/model/thread change; reopened fallback is explicitly estimated. Do not expand #64 into a new occupancy dashboard. Prefer existing UI context surfaces and minimal labels/help only where a value is already displayed.

Content-free diagnostics must identify summary-input preflight vs post-summary target-check rejection; if detailed durable statuses cannot be extended without migration, use typed runtime errors/events while retaining existing durable code compatibility. The user-facing over_limit copy must describe a local budget check without asserting the actual provider/model capacity was exceeded. Original error/status history remains authoritative.
