# Permission reset recovery — development stage

This supplements the D4 recoverable reset protocol. It does not reduce full-card acceptance: initiating reset still requires the application-wide pause, active-run Stop and trustworthy cleanup evidence; Bash and remaining UI remain outstanding. No local Vega execution, compilation, test, migration or user configuration change is permitted. Existing Actions execute development tests; native integration remains user hand-test.

## Recovery service contract

- Resume only an existing, valid pending journal. No journal means no reset; a completed journal does not initiate another reset. A missing/inconsistent journal fails closed.
- Acquire the authority coordination guard and exact database admission pause, then require all existing owners released. This is an application-owner check, not proof of external-process exit. Persisted streaming messages, active automation claims, active/unreleased delegated executions, unresolved effect-capable calls, unknown credential continuations or unknown command-scope results block recovery without normalizing those records.
- Validate and revoke automation authorization through typed tasks. Verify JSON identities/revision match their indexed columns; pause active tasks, clear authorization on all affected statuses, increment affected revision once, preserve payload/usage/blocker history, and never finish an uncertain claim to pass reset.
- Open an existing canonical configuration under its writer lock. Missing/invalid configuration or a changed canonical source fails; never initialize a missing configuration. Accept only the journal's exact raw permission source or its already-reset target, preserve unrelated preferences, save Confirm/no grant/exact target revision atomically, and read back before completing the journal.
- Recovery is idempotent across the DB/config boundary: any failure after pending remains pending; retries use the same journal id, epoch and target revision. Configuration conflict does not overwrite a competing edit. Completion/commit uncertainty is not a success receipt.
- Startup must check pending reset before ordinary automation recovery can normalize active claims. If recovery cannot complete, automatic scheduling stays unavailable and subsequent execution continues to fail closed. The startup call must not claim to have stopped native processes or repaired earlier FullAccess effects.

## Startup and upstream resume integration

- The application first opens a restricted startup view. A background conversation service opens/migrates the selected database, resumes any pending reset, loads or initializes configuration only after reset recovery succeeds, and then performs ordinary automation startup recovery. The main window, sidebar, Settings, MCP registration and execution-capable controllers are not initialized before this service succeeds. The sidebar receives the same opened Store and loaded configuration instead of reopening them.
- Appearance may be read from an existing configuration without creation. A missing, malformed or conflicting pending-reset configuration remains untouched. Failure keeps the startup view visible with an actionable localized error, Retry and Quit; keyboard Tab/Shift-Tab and Enter/Space work, Escape cannot dismiss the gate. Retry is unavailable while the actual worker is running. Successful startup replaces the gate with the normal workspace, without a redundant success banner or a downgrade-safe claim. Automation readiness defaults false.
- Update launch and workspace readiness are different facts. Start the recovery worker only after the restricted window has opened. Before any database migration/recovery/config creation, the worker validates the update/candidate identity and atomically renames the verified `previous.app` backup to `recovery.app`, then validates its identity again and syncs the staging directory before publishing `startup-ok`. This is the rollback-exclusion handoff: an older helper that already observed an absent receipt still fails its mandatory previous.app verification before moving the candidate. A write receipt or timing delay alone is not a handoff. Missing/conflicting/changed backup identity refuses recovery; retries accept only the verified moved backup, never overwrite an existing destination, and retain all evidence. These operations do not enable workspace execution. Updated helpers wait for a separate `workspace-ready` receipt before cleaning the verified recovery backup; after candidate spawn, exit/timeout without readiness retains candidate/backup/records. Pre-launch replacement/spawn failures keep existing rollback. A legacy helper may report cleanup-required because previous.app has moved, but cannot automatically restore it; no workspace/reset/downgrade-success claim follows. Handoff/publication failure blocks recovery before data mutation.
- Upstream interrupted-task resume must not introduce a new authority path. Both history eligibility and the actual preparation transaction require reset replay eligibility and the original persisted run fence to equal the valid current fence. Missing/malformed/changed authority is not regenerated from current settings. Reset rejects pre-cutoff interrupted tails even after its journal completes; fresh post-reset work may become eligible normally. Generic preparation checks pending before normalizing streaming/tool evidence.

## Required development checks

Use isolated database/config fixtures and the real recovery service. Cover source and already-target recovery, retained unrelated preferences, missing/malformed/conflicting config, automation authorization on active and paused tasks, indexed-data mismatch/revision overflow, pending startup refusal before claim normalization, and unsettled-work preservation. No real credentials or external process/network execution. Add startup-service cases for pending + missing configuration (no creation or normalization), successful recovery before config publication/automation readiness, and ordinary first-start initialization only on ready storage. Add interrupted-resume positive and revoked/missing/changed-fence cases using real persistence and preparation decisions, not source-text assertions. Draw a real GPUI startup window and dispatch keyboard events to verify failure focus, Tab/Shift-Tab, Enter/Space retry through the actual background service, Escape containment, and absence of workspace globals before success. The fixture uses an isolated unsupported-version database; it never starts the ordinary workspace or reads user configuration. Add isolated, process-free updater regressions that exercise the production receipt/exit/timeout decision and finalization against temporary candidate/backup/record files: gate-open then quit and unacknowledged exit retain them; a launch receipt alone never permits cleanup; only verified workspace readiness does. Deterministically reproduce the legacy helper's absent-receipt check, perform the production backup handoff and receipt publication, then invoke its actual rollback path with isolated identity verification: it must refuse before moving the candidate. Cover handoff retry, conflicting destination and changed backup without overwriting either source.
