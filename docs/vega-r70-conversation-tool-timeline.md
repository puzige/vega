# R70 — Conversation text and tool cards follow the event timeline

Status: user-authorized bug fix, 2026-09-18. This locally supersedes the S8/C7 history rule that attaches every tool card after the complete owning assistant message. It does not change Agent Loop execution, permission decisions, tool auditing, or provider context.

## Observed defect

One Agent run owns a single durable assistant message. Its `TextDelta` events append to one `MarkdownStream` entry while each `ToolCallProposed` appends a separate card after that entry. The assistant entry later expands in place with every post-tool response, so all text appears before all tools. `vega_conversation::history::project_rows` repeats that order on reopen by projecting the entire assistant content before its tool rows. The screenshots show this: narrative about each search appears first, and the bash/glob calls appear together at the end. It obscures the actual `text → tool → result → continued text` flow and can join independent Markdown fragments into one malformed block.

## Contract

1. A conversation turn renders in the order accepted by the existing event stream: each nonempty assistant text segment, then tool cards at their proposal position, then later assistant text in a new segment. Multiple tool proposals without intervening text remain in audit `seq` order at the same position. A tool card stays in place while approval/running/output/terminal state changes; completion must not move or duplicate it. Preserve the existing pending permission card and terminal/error semantics.
2. Do not concatenate across a tool boundary for display. Each visible assistant segment owns an independently finalized Markdown stream, so a code fence/table/list before a tool cannot consume text from a later provider round. Concatenating visible segment strings in timeline order must equal the original durable `messages.content` byte-for-byte; no added delimiter, duplicated token, or omitted text. Empty segments are not visible. If failure/interruption occurs after the last tool with no later text, its bounded terminal indication belongs at the tail, not before the tool.
3. Keep one assistant message and its existing audit/usage/summary identity per Agent run. Do not add a new execution loop, provider call, message row per tool, or public UI SQLite access. The change is a display chronology, not a change to tool execution or conversation context.
4. Persist the display boundary when a tool audit row is first inserted. Add a nullable nonnegative `tool_calls.text_offset_bytes` through the next additive migration (no seventh table). For new `ToolCallProposed` and direct validation-rejection rows, save the current UTF-8 byte length of the already-durable owning assistant content in the same persistence operation as the audit row. Several proposals may share one offset. Do not edit tool input/audit JSON to carry UI metadata. Existing rows receive `NULL` and are never guessed/backfilled.
5. History paging reads the offset in the existing batched tool query and splits the one message content at valid UTF-8 boundaries in ascending `(text_offset_bytes, tool seq)` order. A non-NULL offset must be within content length and on a `str` boundary; offsets must not decrease in tool-seq order. Corrupt new metadata fails closed with a typed history error. For a legacy message whose tool offsets are `NULL` (or mixed NULL/non-NULL), retain the old text-then-tools display: exact interleaving cannot be reconstructed from previously concatenated text, and timestamp/text heuristics are forbidden. The page remains one message-level keyset unit with a constant number of SQL queries and no raw tool inputs exposed to UI.
6. A completed task summary stays after the last text/tool entry of its owning assistant message. Plan review, artifact, scroll-follow, pagination/prepend anchoring, and route-switch fencing must not regress. UI rendering uses typed history/events only; `rg -n 'rusqlite' crates/vega_ui/src/` remains empty.

## Acceptance

- Drive the real conversation controller with a scripted provider producing `甲` → tool A → `乙` → tools B/C → `丙`, with real audited tools behind the existing owned-temp boundary. Assert persisted content is exactly `甲乙丙`, each tool row has the correct byte offset, tool/usage audits retain their existing message identity, and the live mounted conversation entries appear `甲, A, 乙, B, C, 丙` before and after terminal completion.
- Reopen/restart the thread through the production typed history page and mounted UI; assert the same visible order, no duplicate cards, the summary at the end, and correct status/result updates. Include a multi-byte UTF-8 split and an interrupted/failed run after a tool. Exercise page prepend/scroll follow with more than one message.
- Migrate an owned pre-R70 database and assert old `NULL` offsets keep the legacy order without inventing boundaries; new calls on the migrated database use exact offsets. Reject an out-of-range, non-character-boundary, or decreasing offset without leaking raw audit content. Keep page query count bounded and six-table schema intact.
- Run `cargo fmt --all -- --check`, `./scripts/cargo-lock.sh clippy --workspace --all-targets -- -D warnings`, `./scripts/cargo-lock.sh test --workspace`, package/signature and a native UI check using a disposable test thread. Never alter or delete an existing user conversation as a test.

No new dependency, no non-test `unwrap`/`expect`, no unsafe approximation of old content, and no new user-facing configuration.
