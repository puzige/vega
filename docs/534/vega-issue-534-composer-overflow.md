# #534 Composer 图片与长草稿溢出修复

版本：v1，2026-10-22。来源：[Issue #534](https://github.com/puzige/vega/issues/534)。
生产基线：`e4f18c656aa69d192d095a4338a2108e6c9a3c2c`。

## 目标、范围与事实

- 用户报告：大图片遮挡下方输入文字；长草稿没有滚动条，无法向上回看。
- 当前 `ConversationStream::render_composer` 顺序为附件、输入、底部操作；首页与会话共用入口。
- 附件经 `render_attachments` → `ImagePreview::thumbnail` → `thumbnail_sized`，名义尺寸为现有 `Layout::ATTACHMENT_THUMBNAIL`，但图片子节点没有显式溢出裁剪。实际解码后的布局和绘制是否溢出须由先行测试确认，不把静态推断当作已复现。
- `TextInput::new_multiline` 的 Composer 视口限制为 1–8 个视觉行；`first_visible_row` 支持光标跟随，但滚轮只在 `scrollable_editor` 模式注册。Composer 不启用此模式，也不提供滚动条。这是已静态确认的长草稿根因。
- 保留原图、导入限制、附件移除和预览、发送数据、预测、IME、单行字段及现有大编辑器的契约。不改依赖版本、权限、模型或运行时逻辑，不新增产品解释文案。

## 实现前验收矩阵

所有自动测试为进程内真实 GPUI 组件行为测试，隔离文件系统、外部应用和服务。本地不运行 Vega、构建或测试；由现有 draft PR Actions 执行。

| ID | 场景与操作 | 可观察结果与必需回归 |
|---|---|---|
| A1 | 大尺寸横图、竖图、方图的缩略图，完成解码后绘制 | 可见图片绘制被缩略图边界约束，原始宽高比不撑大附件区域；下方输入文字与图片不重叠。不能只检查空白占位节点 |
| A2 | 同时添加多张图，在宽、窄布局中渲染实际附件区域与输入 | 附件换行后区域保留真实高度，输入与底部发送/模型操作位于其后；移除按钮、点击预览及键盘入口仍可用 |
| A3 | 超过 8 个视觉行的草稿，滚轮/触控板向上、向下滚动 | 首尾内容均可到达；内容、选区、焦点不因滚动改变；停止滚动后重绘不会立刻跳回光标 |
| A4 | 长草稿的滚动条，拖动滑块或点击轨道到首尾 | 可见且可操作的垂直滚动条与内容位置同步；只在有溢出时出现，不遮挡文字；沿用主题和现有滚动控件惯例 |
| A5 | 空、单行、恰好 8 行以及超出 8 行；长中文和英文自动折行 | 仍按视觉行自适应 1–8 行，只有实际溢出才滚动；短内容无多余滚动条；窄宽变化后滚动范围有效 |
| A6 | 上滚后移动光标或编辑；IME 替换；清空/替换长草稿 | 编辑/光标变化后需要时重新显示光标；内容和组合输入保真；清空或缩短后滚动位置、滚动条有效复位；发送仍使用完整草稿而非可见片段 |
| A7 | 不溢出以及滚动到顶部/底部，重复滚轮输入 | 不越界；不能消费的滚动不被无条件吞掉；滚动本身不触发编辑或发送 |
| A8 | 单行字段与 `with_editor_viewport` 大编辑器阳性对照 | 单行字段不新增滚动行为；现有大编辑器仍可滚动、光标跟随和编辑；不把 Composer 的 8 行限制应用到大编辑器 |

自动证据须观察生产组件布局、可见文本/绘制、真实滚动事件及拖动后的可见结果，不用源码字符串、镜像算法或仅私有字段断言替代。必要的短内容/现有编辑器阳性对照随首轮测试一起提交。图片绘制可用 GPUI 绘制场景/内容 mask 与布局边界观测；不能把缺失渲染器的截图 API 失败算产品 RED。

用户手测：合并后的云端发布版本中，在首页与已有会话分别粘贴大图和长中英文草稿，检查浅/深色、窄窗口、触控板滚动及滑块拖动，确认预览/移除/发送入口可用。Agent 不用本地运行或合成焦点事件替代用户真实手测。

## 实现计划（验收先行）

1. 专职实现 Agent 在生产未改时写齐测试及必要 dev-only 接线；静态核对 GPUI Kit **实际锁定 0.6.1** 与 `gpui-pre 0.3.4` API。设计文档中 0.6.0 是历史说明，不回退依赖。
2. 主 Agent 组织非写入者独立审查测试；建立 draft PR，现有 Actions 确认有效 RED。无关编译、字体、解码、runner 或依赖错误先修观察层，不算产品 RED。
3. 有效 RED 后冻结测试内容与预期。专职实现 Agent 最小修复图片尺寸/裁剪与附件布局，以及多行输入的滚动、滚动条和光标跟随协调；保留单行与大编辑器行为。滚动/绘制控件使用已有主题 token，不硬编码颜色或字号，不加代码注释。
4. 同一冻结测试云端 GREEN，独立审查停写版本；在 PR 固定完整提交、原始测试 patch、RED/GREEN run/job 与准确计数。
5. 另一个独立提交仅删除 Rust 测试及独占接线。审查生产无差异，对最终 head 执行现有完整门禁，确认 Rust 0 发现/0 执行（`no Rust tests`，不是 Rust 测试通过）。
6. 最新 head required check 通过后转正式 PR、squash merge；Issue 保持开放，Project 置 In review 等用户手测，不自动关闭。

## 数值与约束核对

- 缩略图边长沿用 `Layout::ATTACHMENT_THUMBNAIL = 72`；单张布局范围为 72 × 72，不由原图分辨率决定。
- Composer 可见行数满足 `1 <= visible <= 8`；总行数 `T`、可见行数 `V` 时，合法首行范围为 `0..=max(T - V, 0)`。
- 例如 20 行、8 行视口：首行从 0 到 12，最后可见范围为第 13–20 行；8 行、8 行视口：范围仅为 0，无滚动条。
- 这些是既有尺寸和用户要求的边界，不引入新的全局布局 token。若测试发现遗漏边界或需要改变验收，先记录变化并重开 TEST-FIRST，不能实现后补测追认。
