## Correction and scope

PR #561 implemented and tested the specified timer, but the specification incorrectly converted a diagnostic rule into automatic cancellation. Neither #514 nor Harness² established an optimal stage duration. This revision supersedes B1–B4's automatic expiry and C5's blanket rejection of interrupted recovery in `native-execution-bounds.md`; the original evidence remains historical evidence for that implementation, not evidence of faster delivery.

Elapsed time alone must never cancel a delegated execution. Explicit user/parent cancellation, existing permission rules and model-context admission remain effective. The original 20-minute no-new-artifact diagnostic remains a diagnosis rule, without automatic restart, replacement or a promise of a reviewable patch by that time.

A checkpoint is durable recovery information. A reviewable artifact is a separately identified, stopped version with a declared scope and evidence. Completion text, a cancellation receipt, an elapsed deadline or a model's assertion of READY cannot establish either durable recovery or independent review/CI success.

## Implementation boundaries

Use one implementation writer. Prefer a small structured stage checkpoint surface and a distinct `resume_agent` operation; ordinary completed `followup_agent` keeps its existing meaning. Shared public types go through the existing conversation types boundary. Persist recovery metadata with additive migrations and transactional updates; do not change the installed application or migrate the user's actual database during this task. Reuse approved dependencies and existing read/checkpoint/safety capabilities.

The tool and storage schema below is grounded in the actual APIs and supports both cooperative checkpoint publication and honest reconstruction after interruption. A non-ready checkpoint call does not stop a stage; a terminal handoff adds stopped ownership separately. External validation references identify existing jobs/checks; publishing a checkpoint never starts them.

### Runtime surfaces

- Child-only `checkpoint_stage`: `stage`, `summary`, `artifacts` (`path`, `read_call_id`), `evidence_call_ids`, `unresolved`, `next_step`, `ready_for_review`. The runtime derives raw-byte SHA256; the model is not asked to calculate or supply it. A non-ready declaration persists and continues. A ready declaration is exclusive within its tool batch; successful validation ends this stage without another provider request or later tool dispatch, then drains/persists/releases normally. The parent's handoff becomes review-ready only after that lifecycle succeeds. A rejected declaration leaves no ready claim. The declared scope/summary are agent claims; exact read content and successful tool references are runtime facts.
- Parent-only `resume_agent`: `agent_id`, expected `message_id`, `checkpoint_id`, expected `source_version` and `source_fingerprint`, `task`, and explicit per-call `reconciliations` (`call_id`, `evidence_call_ids`, `resolution`). It creates a new execution ordinal in the same child conversation. The new parent run must belong to the same owning parent conversation. Resume is explicit, idempotent by tool call, and never an automatic retry. Ordinary completed followup remains separate.
- Persist append-only stage checkpoint records, including execution identity, origin (`declared` or system-origin `interrupted`), source fence, manifest, unknown-effect identities and creation time. Add durable execution release and resume linkage with an additive migration. A final interruption checkpoint records the final source fence and actual tool outcomes, even if no earlier declaration exists. Preserve the prior declaration/provenance separately when one existed; `interrupted` alone does not imply there was no declaration. Keep original timestamps and prior parent-run links.
- A delegated execution's admitted `message_id` stays its stable public identity. Accepted user steering can create additional assistant-message segments inside that same execution. Persist a private exact execution-to-segment association at registration and inherit it transactionally only through actual `SteeringAccepted`; never infer ownership from later timestamps or a shared thread alone. Validate each Read against its real tool-call/message identity and then bind its receipt to the owning execution. Handoff, unknown effects, partial output and legitimate completion lookup cover that execution's associated segments. Unrelated/manual continuations gain no association. Recovery still creates one new execution ordinal in the same child, retains all stored user steering/attachments and rejects stale/unowned source. This preserves R5/R9/R10 rather than silently disabling checkpoints after steering.
- Artifact support initially covers ordinary text files supported by the existing Read pipeline, including untracked files; other useful evidence is retained by message/tool references. A matching declared hash without a successful authorized complete Read does not establish identity. Revalidation uses the same path, credential and identity protections. No whole-workspace scan or new Git executor is required.
- Preserve potentially effected running/failed/cancelled external tool identities before recovery normalizes audit statuses. Resolution must cover each unknown effect with a concrete disposition and accessible existing evidence; the runtime checks provenance, not the truth of a model's prose. A cancelled external command is not proof that nothing happened. External validation IDs are carried forward and inspected, not resubmitted.
- Hold a nonblocking OS exclusive execution lock from child admission through terminal persistence and host release, using the existing approved `libc` dependency and an owner-only private location derived from database/child identity. Preserve existing in-process occupancy/CAS as well. Do not infer dead ownership from a timestamp or TTL. On process recreation, only acquiring the same lock permits abandoned-native-owner recovery; distinguish this from a successful prior host release. The lock proves native writer exclusivity, not termination of an external descendant: unresolved external effects still require explicit reconciliation before dispatch. Unsafe lock paths, unavailable proof or persistence/release failure fail closed.
- Recovery projection retains every stored user instruction/attachment, the selected checkpoint and original interrupted-stage outcomes/partial output with exact provenance. Tool results stay lower trust and original deduplication authority stays in the audit store. Existing privacy filtering may already omit sensitive wire data; this feature cannot reconstruct it and must not promise to do so. If required recovery information exceeds inherited context admission, reject explicitly instead of omitting constraints.

### Observable receipts

Successful `checkpoint_stage` returns `checkpoint` with `id`, `agent_id`, `message_id`, `origin`, `source_version`, `source_fingerprint`, `manifest` and `unknown_effects`; its outer `ready_for_review` is false while execution is still live. Persisted terminal checkpoint metadata uses the final source fence. `wait_agent`/`list_agents` expose each agent's latest `checkpoint`, `release_state` and `ready_for_review`, alongside their existing identity/state/result fields. A normal completion without a successful ready declaration remains `ready_for_review=false`.

`list_agents` in a subsequent run reads the latest children/checkpoints belonging to the same parent conversation, so an explicit resume can obtain durable checkpoint/source identities without an additional history tool. This must not expand inspection to unrelated conversations. Registry-local live state and the ownership lock take precedence over an apparent durable terminal state. Preserve existing receipt credential validation and size limits; an unavailable/incomplete recovery receipt is explicit rather than silently dropping required fields. Review-ready identifies the validated published version at handoff, not a guarantee that unrelated later workspace writes cannot change it; resume revalidates the actual artifacts.

The tests cover the eight native groups: long-running child plus explicit cancellation; checkpoint continue versus terminal handoff; file/evidence authority and changed artifacts; persistence/release failure; same-parent new-run/reload and concurrent ownership; stale/source/authority/call-id rejection; unknown-effect reconciliation and zero duplicate dispatch; interruption without a declaration and complete bounded recovery context. These are acceptance groups, not a required test-count target.

The private lock location is the database directory's `delegated-owner-locks/<child_id>.lock`; it never enters model receipts or logs. Use 0700 owner-only directory and 0600 owner-only regular single-link file checks, validate the child ID as a safe component, and prevent symlink/path-replacement races with descriptor-scoped no-follow opens or an equivalent existing safe facility. A native integration case holds the actual OS lock through the existing approved `libc` boundary, observes resume rejection with zero provider dispatch, then releases it and observes successful admission. This is stronger evidence than racing two in-memory supervisors, without starting another process.

### Architecture-review boundaries fixed before RED

All delegated recovery normalization paths, including history restart/loading and ordinary pipeline preparation, must acquire the same OS ownership proof before changing active message/tool/execution statuses. Keep that proof while capturing pre-normalization unknown effects, normalizing and establishing the final source fence. A locked child remains untouched when history is loaded. Use separately opened descriptors that actually conflict and `CLOEXEC`; no child tool process may accidentally inherit ownership proof.

Persistence or host-release failure must remain quarantined across a new parent run/history load in the same live process. Returning from the failed lifecycle and dropping its local descriptor is not proof of process death or a confirmed release. Retain the ownership barrier or use durable failure/owner-instance proof so a new supervisor cannot reinterpret that failure as abandoned-owner recovery. Include this action in the release-failure test, as well as ordinary same-registry admission rejection.

An armed lifecycle guard covers direct future destruction as well as explicit error returns. Arm it before an operation can acquire execution/host ownership; disarm only after confirmed drain, durable terminal/release state and successful host release, or confirmed absence of acquired ownership. If the provider or host-release future is dropped, retain the OS ownership barrier and quarantine rather than letting history, a new Supervisor or ordinary preparation normalize/admit a replacement. PersistenceActor's temporary clone and the in-memory live marker are not substitutes for this guard.

Host admission cancellation must distinguish confirmed rejection from accepted or uncertain ownership. Once admission has been sent to the native host, a cancellation winning the caller's acknowledgement race does not prove that the UI stayed idle. Await the accepted admission's cleanup/release, or keep uncertain ownership quarantined. Pre-dispatch validation/admission failure sends an explicitly failed/interrupted terminal snapshot, never a Running snapshot as Finished. Cover cancellation after host acceptance but before the caller observes its acknowledgement; immediate-Ok TestHost behavior alone does not validate this window.

Persist call-bound Read receipts only from real successful authorized Read execution and its durable audit. Bind child/execution/call, canonical file identity, raw-byte hash, authority and completeness. A complete artifact read has no offset/limit restriction and no line/result truncation; partial reads or Write/Edit's read-state updates never qualify. Raw CRLF/UTF-16 identity must come from original bytes, not rendered text. Resume/revalidation of external files must go through the current Read permission layer, not merely `Tools::read`. A prior authorization is not a new unrestricted permission.

Artifact revalidation is an internal runtime Read, so it has no model-origin ToolCard proposal. The existing permission presenter otherwise defers requests until their matching ToolCard appears. Use a private, runtime-created validation origin on the existing pending-permission lease and a dedicated internal queue/adapter entry for this Read only; the presenter may show its existing PermissionCard without inventing a model proposal. Restrict that internal origin to a validated absolute-path Read with no danger, external-call or ACP identity. It offers Allow once and Deny; it cannot create a permanent permission rule. Suppress the unavailable Always action in rendering, keyboard traversal/action and responder validation, without mislabelling the request as an external tool. Ordinary tool/MCP requests retain their exact ToolCard/target checks. A tool input, call-id prefix or tool name cannot grant the internal origin. Existing request validation, cancellation/timeout, Settings/thread teardown, responder latch and display-target checks remain effective; no new presentation style is introduced. Validate the ordinary-versus-internal presentation/decision boundary with the smallest suitable stable regression; native UI use remains subject to user manual acceptance.

A successful ready checkpoint produces a distinct runtime-origin stage-handoff terminal outcome carrying its checkpoint identity. Do not synthesize model final-response metadata or relax ordinary model-completed response validation. Persist the handoff provenance and project its manifest as lower-trust task data in the next stage. After release, that completed handoff may use ordinary same-parent-run `followup_agent`; its checkpoint replaces the absent model final only in the explicitly typed handoff branch. `resume_agent` handles interrupted stages, including a later run of the same parent conversation. The test must exercise the real checkpoint tool through terminal persistence/release and a subsequent continuation, without fixtures inventing model final metadata.

Do not add a global scheduler, new background service, automatic online strategy search, general workspace backup, arbitrary process killing, CI workflow changes or a new deadline disguised as a checkpoint mechanism. Runtime correctness and research strategy effectiveness have separate evidence.

Correctness tests prove safe handoff/recovery, not speed. Preserve #514's full 8h29m36.512s start-to-terminal observational record including cancellations; it is not a controlled baseline. Keep independent review and final exact-head CI in both compared variants.
