# 对话打开路径减负（#730，第一批）

## 范围与证据

用户反馈置顶对话有时显示 Logo shimmer，而项目内对话会卡顿且不显示，随后授权「先把已经发现的这一个路径先修」。调查基线：`bbe1df89faf3c9bdca934ade5593cca25ade4389`。实现前 fetch 并快进至 `26e56eb3e07983485a95c3c03eef29e15006ec57`（#732 工具复制区域 hover，未触及本批路径）。

静态确认：置顶和项目内对话行共用 `ThreadsBlock::open_thread`；访问记录已在后台执行，但完成前没有内容区等待反馈。成功后 `ThreadsBlockEvent::Opened` 同步刷新项目列表。未缓存对话在后台读取历史，但 `render` 内的 `apply_history_page` 同步解析助手 Markdown、生成行模型，然后才返回正文元素。150ms 防闪烁只计算历史读取等待，未覆盖访问与正文预处理。

这些是已确认的执行边界，不是用户卡顿的实测归因。未证明置顶属性本身影响加载。不得宣称固定帧率、零卡顿或本批解决全部 #730。

## 最小方案

1. `ThreadsBlock` 保存访问等待的目标与点击时间，原串行访问及最后意图机制保留。通过既有 Sidebar 事件层通知根视图；150ms 定时唤醒只更新界面，不阻塞线程。Sidebar 提供只读等待投影。路由变化清理投影，成功交接历史加载时沿用点击时间。
2. `ConversationLoading` 区分访问等待与已启动的数据 worker。等待反馈不提前改 `OpenedThread`。历史 worker 在读库后调用 UI 模块的纯数据准备函数，返回一次性 UI 提交闭包（不传输 UI entity）。加载成功只在预处理结束后公布。实际路由与 generation fence、失败重试保持。
3. 在 `conversation_stream` 内提取私有初始历史准备结构。保留原 response 分段与生成通知算法；在 worker 构建助手 `MarkdownStream`、`StreamModel` 和 owned 文本。UI 只组装 MessageCopy/实体并应用原列表、计划、队列和锚点逻辑。不改变流式增量解析或分页请求生命周期，不新增依赖、不搬动主存储连接、不削弱隐私处理。UI 安装时仅对含生成通知的正文核对当前投影，语言未变化不重新解析；准备期间发生语言切换时按当前语言更新，避免旧语言显示。公开入口返回一次性闭包，不引入跨 crate 重复 DTO。
4. 对话打开触发的 `ProjectsBlock` 列表刷新改成后台连接查询，合并重复请求，以 generation、数据库身份和排序校验结果；其他权威列表更新使旧查询失效。本批不扩到项目标题写入、初始化及其他同步交互。
5. 保留低开销、无正文/路径的读取、准备、UI 应用耗时诊断，供后续有授权的手测定位。必须在 UI 上完成的实体建立、列表整理、首次布局仍可能耗时；本批不做无证据的分页/批次重写，不承诺已达到性能预算。

## 非目标

导航前进/后退、命令面板、通知访问写入，置顶/归档/重命名/项目标题写入、模式切换、审批以及全仓库审计留在 #730 后续。启动画面外观、Markdown 引擎、数据库 schema、依赖、权限与存储协调不改。不强制动画停留，不将动画出现当成流畅性证据。

## 验证与交付

本地只做低 CPU 静态、格式、差异检查，不运行 Vega、编译、构建或测试。独立审查检查本次异步边界、所有者/代次、原语义保全与失败出口。完整最终 head 经原 `pr-check`（fmt、Clippy、保留 Python、Nextest 清点/执行）后才合并；Rust 空集明确写 `no Rust tests`。如采用开发 Rust 测试须先固定云端证据再移除，不留下 master 测试或接线。

实机流畅度、加载反馈时序及视觉由用户手测；当前无性能测量结果。合并后 #730 保持开放，本批交用户验收，其余范围不标完成。回滚以本批 squash commit revert 为边界，不修改用户数据库或配置。
