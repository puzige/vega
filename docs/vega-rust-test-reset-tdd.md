# Rust 测试清零与测试先行规则（历史规格）

**已被取代的历史规格**：本文下方的清零范围、强制测试先行/RED/GREEN/冻结/禁止补测流程与验证记录仅用于解释当时操作，不是当前交付要求。现行规则以 [验证与快速交付政策](vega-rust-test-delivery-lifecycle.md) 和 [执行指南 §7.2](vega-exec-guide.md#72-快速交付与按风险验证当前规则) 为准：取消强制 TDD，按风险验证；Rust 测试可在开发分支辅助并留痕，但合并前必须清理，不得进入 master。现存 Python 测试保留；历史原文与证据不重写。

## 用户裁决与范围

用户在历史编号清理合并后，明确选择“只清零 Rust 测试，再建立规则”。本规格的最初清零从 master 基线 `cf00946e` 开始，是当时对“保留现存 Rust 测试”的一次性例外。后续用户要求 Rust 测试仅在开发阶段保留到 GREEN，最终交付前必须删除；该授权不允许删掉失败/未执行测试来逃避验证。

执行期间远端新增 `abd5dc67`（侧边栏持久排序）与 `a608ffa2`（滚动边缘渐隐），后者作为本轮最终集成基线。保留两项功能的生产实现，将其中分别新增的 9 个、18 个 Rust 测试一并纳入本次清零；原始基线的 1,587 个加上新增 27 个，合计 1,614 个测试定义。

- 删除当前整个 workspace（含 `xtask`）的 Rust 单元、集成、GPUI、属性测试及可执行 doctest，以及仅为这些测试服务的 fixture、helper、测试开关、模块入口和依赖接线。
- 混合源文件按语法项/条件编译边界删除，不按文件名或模糊正则批量删生产代码。条件分支保留原 `cfg(not(test))` 的生产路径；保留 `unsafe` 所需安全说明。
- 保留应用、工具、打包和 benchmark 的非测试实现、生产安全检查、业务数据、migrations；不要把 production 的 assertion、名称含 test 的业务操作或 benchmark 执行器误判为测试。
- 保留现有 Python 发布、组件准备和 delta 脚本测试及其 fixture，保持字节不变。不删除通用的 Cargo/Nextest、格式或 Clippy 检查能力。
- 保留 `docs/` 历史记录，不把历史报告伪装成本次验证结果。新增规则和清零说明只记录在当前规则入口及本文件，不批量改写历史规格。

## 后续强制顺序

适用于主 agent、子 agent、Feature 与 Bug 修复：

1. **验收先于实现**：从需求/spec 写出最少、可观察的行为与失败边界；没有对应行为变化的文档/格式改动不凭空添加测试。
2. **先写测试**：在新增或修改本轮生产实现之前，写齐本轮验收所需测试。记录测试先行提交/补丁和实现尚未修改的基线。
3. **确认 RED**：按仓库执行限制交 Actions 验证，确认测试因目标行为缺失而失败；无关编译错误、缺依赖、网络/runner 故障不算有效 RED。API 不存在时，最小接口缺失可记录为 RED，但须说明尚未覆盖行为，不得冒充断言已执行。未经确认不进入实现。
4. **再写实现与 GREEN**：冻结本轮测试目标与预期后写最小实现，运行相同测试及完整 PR gate。实现阶段不新增事后证明实现的测试，不放宽断言、不改期望、不 ignore、不靠重试换绿。
5. **GREEN 后删测**：先在 draft PR 固定带测试提交的原始源码/补丁、完整 SHA、RED 原因与同一测试 GREEN 的 Actions run/job/准确计数，再用独立提交删除 Rust 测试及独占 fixture/mock/helper/feature/dev dependency；生产、benchmark、Python 和通用 CI 能力不变。
6. **最终门禁与正式 PR**：审查生产差异和独占支持残留，验证删测后最新 head 的完整 PR gate。Rust 必须 0 发现/0 执行、标 `no Rust tests`；不是 Rust 测试通过或带测试 GREEN 的替代。证据可核实且门禁成功后才把 draft 转正式 PR/申请合并。
7. **实现完成后禁止补测**：不得先写实现再补测试、按实现输出反推断言，或为报告/覆盖率增加用例。发现需求遗漏、新边界或新 Bug，停止当前轮，先记录独立的验收变化并重新进入“先测后修”；不能用补写用例为已经完成的实现追认测试先行。

纯重构的验证测试也只在开发阶段保留到 GREEN，最终交付前删除。确需修正测试自身错误或测试接线时，先记录证据并审查，不改变验收含义；属于验收变化则重新开始一轮，而不是暗中改测过关。以后新测试必须使用行为名称，不把 issue/task 编号写回非文档代码。

## 有效测试标准

每项测试须能指出具体失败行为、业务不变量或安全边界，验证公开/稳定边界上的结果及必要副作用。优先少量有区分度的正常、失败、恢复样例。

禁止：仅检索源码字符串/函数是否存在、只验证 mock 调用或机械转发、镜像生产算法得到同样答案、重复堆叠相同断言、为内部字段/API 单独造覆盖率测试。mock 可以隔离外部进程/网络/应用，但不能 mock 掉被测业务或安全判断。调用次数仅在“不得重复执行/不得请求”等本身属于业务或安全契约时有效，且须与结果/终态结合。

## CI 与证据

- 保留 required check 名 `check (fmt, clippy, test)`，保留格式、全目标 Clippy、三组 Python 测试与 Nextest runner。
- 清零后 Rust 测试集为空是预期状态，CI 需要显式识别并在日志/摘要标为“当前无 Rust 测试”；不称为“Rust 测试全部通过”。非空测试集仍正常执行，真实失败必须阻断，不用通用 `continue-on-error` 或吞退出码放行。
- 测试先行是审查/交接的必需证据：生产未改的 RED 基线、冻结测试源码/补丁与完整提交 SHA、原始失败原因、实现顺序、带同一测试 GREEN 的提交/run/job，以及独立删测提交和最终 head 空集门禁。PR 须固定可访问的原始测试来源，squash/删分支后仍能找回，不依赖本机临时文件或过期 artifact。最终绿色空集或提交顺序不能单独证明 TDD，不替代带测试 GREEN。
- 本次清零是删除旧测试的维护操作，不人为写一批新 Rust 测试来替代已删除集合。通过静态清点、生产代码差异审查和 PR gate 验证清零，不伪造 RED。
- 默认本地限制保持不变：只做低 CPU 静态/格式检查，编译、Clippy、运行测试交云端；用户此前针对上一轮编号清理的本地执行授权不扩大为全局政策或本轮默认授权。
