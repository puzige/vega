## 1. Product boundary

Vega acts as an **MCP client**, not an MCP server. A user can add, test, authenticate, enable, disable, and inspect local or remote servers entirely in Vega's Settings UI. An enabled, healthy server contributes discovered tools to a new Execute run; the model can propose a call, but Vega's own permission and audit boundary decides whether it is sent. The user sees the server/tool identity, bounded argument preview, approval state, outcome and error in the existing conversation tool-card pattern. Disabled, disconnected or unauthenticated servers contribute no tools and cannot be called by a hallucinated tool name.

V1 includes local stdio, remote Streamable HTTP, modern MCP protocol, an explicit 2025-11-25 compatibility path, `tools/list` and `tools/call`, anonymous and authenticated HTTP, one-call approval, cancellation, reconnect and crash-safe audit. It does **not** add remote legacy HTTP+SSE transport, an MCP server, resources/prompts, sampling/roots/elicitation, MRTR interaction UI, Tasks/MCP Apps extensions, plugin marketplace, or Skill loading (#74). An unsupported content block or protocol capability produces a visible typed failure; it is never silently discarded or converted into fictitious text.

The existing feature list's “stdio/SSE” line predates [MCP 2026-07-28 transports](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports). Streamable HTTP may return a request-scoped SSE **response**; that is not the deprecated standalone HTTP+SSE transport. The [current HTTP transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) requires both JSON and request-scoped SSE response handling.

## 2. UI and durable configuration

1. Settings has an MCP page with local/remote server list, add/edit form, explicit enable/disable, connect/test, refresh tools, auth state, last content-free error, and per-server tool names. A new server starts **disabled**. Saving an incomplete form never launches a process or sends a request. Enablement, deletion and auth changes happen only through UI; no user-edited TOML/SQLite is required for acceptance. Removing a server or disconnecting credentials requires a clear confirmation and does not erase historical tool-call records. “Disconnect and clear credentials” removes local tokens/secret references and stops reconnection; UI states that this may **not** revoke the remote service's authorization grant and directs the user to that service when necessary.
2. Each server has a Vega-owned stable ID and configuration revision; display name and MCP `serverInfo` are not authority. Local entry: executable and argument vector (no shell interpolation), optional explicit working directory, and individually selected environment credential references. Default working directory is an app-owned directory, never the user's project root; no wholesale parent environment or credential forwarding. A user must explicitly approve the command and relevant filesystem/network authority at activation. An MCP child is **not** contained by Vega's built-in bash Seatbelt profile; UI must not imply that it is.
3. Remote entry: exact MCP endpoint URL, auth mode (`none`, OAuth, or explicit bearer-secret reference), and enabled state. HTTPS is required except an explicit loopback-only development setting for `127.0.0.1`/`::1` (not arbitrary private hosts). No username/password, token, access key, client secret or refresh token appears in config.toml, project files, SQLite, tool descriptions, events, cards or logs. Credentials live under the existing config-root owner-only credential discipline; records are scoped by exact endpoint/resource and, for OAuth, issuer. Disabling a server cancels its in-flight call and prevents every subsequent dispatch, including calls proposed from an already-frozen run catalog. It does not silently revoke the remote grant.
4. Connection states distinguish disabled, connecting, ready, authentication required, incompatible protocol, disconnected, and failed. “Test connection” is a real discovery operation, not a model call. Tool catalogs have an explicit refresh affordance; a running task keeps the immutable catalog snapshot it started with. A removed/changed tool fails visibly rather than silently rebinding its alias.

## 3. Protocol and transport contract

1. Prefer MCP revision **2026-07-28**. For stdio, launch the child with bounded stdin/stdout/stderr, newline-delimited UTF-8 JSON-RPC, request-ID correlation, and `server/discover` version probe. Modern requests carry the required per-request `_meta` version and capabilities. Only if the [official version-detection rules](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning) identify a legacy server may Vega fall back to `initialize`/`notifications/initialized` at pinned `2025-11-25`. A recognized modern version error must negotiate a mutually supported modern version, never trigger a legacy downgrade. No other legacy version is claimed supported.
2. For remote, one POST per JSON-RPC message to the exact configured MCP endpoint; `Accept` includes `application/json` and `text/event-stream`. Handle a single JSON response or a request-scoped SSE response. Send the protocol version in both body `_meta` and `MCP-Protocol-Version`, plus `Mcp-Method`, and `Mcp-Name` on `tools/call`; mirror valid `x-mcp-header` parameters with the spec's header encoding, rejecting malformed annotated tools. Never put bearer tokens in a URL or forward them to a changed origin. Modern HTTP has no session ID, standalone GET stream or `initialize`. A recognized modern error is not a reason to downgrade. Legacy **Streamable HTTP 2025-11-25** may be used only after the documented era check; legacy standalone HTTP+SSE is out of scope. See [transport framing and headers](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http).
3. Discovery consumes all `tools/list` pages with cycle/size/time bounds and validates each input schema as an object. Preserve server tool name case and map `(stable server ID, exact tool name)` to a deterministic provider-safe alias. Aliases cannot collide with built-in tools or with another server. Reject duplicates and unrepresentable names; never resolve by untrusted display name. Server descriptions, schemas and annotations are **untrusted data**, not system instructions or authority. The [tool specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) explicitly treats annotations as untrusted and recommends namespacing aggregation.
4. At run start, freeze enabled/ready server IDs, configuration revisions, exact tool schemas and alias map. Only this snapshot enters the provider request, budget estimator and dispatcher. `tools/list` changing during a run cannot add new capability to that run. A `tools/call` uses only the frozen name and raw arguments after Vega's approval. V1 ceilings: 8 enabled servers, 64 tools per server/128 total, 256 KiB for all advertised schemas, 256 KiB call arguments and projected result, 1 MiB per stdio line or SSE event, 8 MiB cumulative response, 4 MiB cumulative `tools/list` catalog, 15 seconds for connection/discovery, 120 seconds for a call, and 30 seconds with no SSE progress. Crossing a limit fails typed and closed; never truncate JSON into a different call or keep parsing unbounded bytes. Owned E2E fixtures must verify these exact caps. Never auto-follow a resource link or execute instructions found in tool output.
5. V1 projects bounded text and bounded `structuredContent` JSON into the model/tool card, preserving `isError`. Image/audio/resource blocks and `input_required` are explicit unsupported-result errors until a later spec supplies safe handling; no screenshot/image bytes are mislabeled as text. Do not advertise unsupported client capabilities. Protocol errors and tool execution errors remain distinct. A server response is lower-trust data even when it claims `audience=assistant`.
6. The registry is a **single run-start tool authority**, not a second Agent Loop. Each entry needs a stable canonical identity, provider-safe alias, schema, capability/permission class, dispatcher handle and typed audit-projection policy. Built-ins retain their names; MCP aliases are namespaced by Vega's configured server ID. Reserve the unqualified Vega-owned `load_skill({name})` and `read_skill_resource({name,path})` names for #74 rather than allowing an MCP server to claim them. Both MCP and #74 tool schemas enter the same frozen provider list and #76 token estimate, while their distinct permission policies and recovery validators remain explicit. #74 owns a content-free `load_skill` receipt and the frozen full Skill body in the **next-round system envelope** so compaction cannot prune it; MCP results never acquire that authority. #73 does not implement Skill discovery or loading.

## 4. Remote authorization and credential boundary

The [2026-07-28 MCP authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) makes HTTP authorization optional, but when used it specifies protected-resource metadata, authorization-server discovery, client registration, OAuth 2.1/PKCE, resource indicators, and audience binding. Stdio uses explicitly supplied environment credentials rather than the HTTP OAuth flow. **A pasted bearer token is not a substitute for claiming OAuth conformance.**

1. `none` sends no credential. Explicit bearer mode requires the user to select/create an owner-only secret reference in the UI; it sends only to the exact approved HTTPS URL/origin and is labelled non-OAuth. It never imports provider API keys or a token from another MCP server automatically. Reject redirect/downgrade/cross-origin forwarding with an actionable error. For every HTTP redirect or metadata hop, revalidate the destination **before** any Authorization header is attached; never copy a credential to the redirected request by default.
2. OAuth mode follows a 401 `WWW-Authenticate` resource-metadata URL or the specified `.well-known` fallback; validates protected-resource and AS metadata, exact issuer, supported registration method and target `resource`. Support a user-entered **pre-registered client ID** and **Dynamic Client Registration (DCR)** when the validated AS metadata advertises `registration_endpoint`. DCR is deprecated compatibility, never background auto-registration: Settings shows the AS origin, proposed redirect/scopes and deprecation label and requires explicit user confirmation before registration. Register as a native app with `application_type: "native"` where applicable, bind the resulting client identity to the exact AS issuer, and surface registration/redirect-constraint failure without falling back to an untrusted issuer. Client ID Metadata Documents (CIMD) become usable only when Vega has an approved public HTTPS metadata document/identity; an AS that offers only CIMD remains visibly unsupported until that prerequisite exists. Follow the [official registration priority and binding rules](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration). Use system browser + exact loopback/HTTPS redirect, state and PKCE S256; validate callback issuer before code exchange, scope and resource binding, token endpoint and refresh failure. No browser page, server response, or Skill text can complete user consent for Vega.
3. Store access/refresh tokens only in owner-only credential storage, isolated by endpoint/resource + issuer + client identity; never mix authorization servers or pass a provider credential through. Send `Authorization: Bearer` on every authorized request, not in query strings. Step-up scope requests need a new explicit user action, bounded retries and a visible failure. Token expiry/401 pauses further calls; never silently fall back to unauthenticated requests or a different token. Follow [MCP authorization security considerations](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations), including PKCE, issuer and token-audience rules.
4. Network metadata/redirect resolution is a security boundary: allow only HTTPS (except explicit loopback development), validate each origin and issuer, prevent downgrade and private-address redirection from a remote HTTPS endpoint, bound redirect count and response size, and never attach credentials to metadata fetched from an unvalidated origin. First implement codec/HTTP/PKCE with existing approved `reqwest`, `serde_json`, `sha2`, `base64`, `eventsource-stream` and an OS CSPRNG through approved `libc`/OS APIs; entropy failure closes the auth flow, never substitutes a weak RNG. Verify target-OS API availability before coding. Per `vega-exec-guide.md` §3/§5/§6, **every** new crate outside the whitelist is an architect-approval blocker: submit its exact pinned version, license, transitive dependency inventory and why the approved stack cannot meet the requirement, and wait for approval before changing `Cargo.toml` or `Cargo.lock`.

## 5. Vega permission, audit and recovery contract

1. An external MCP server is not a built-in `read` tool. In Ask/Plan, do not advertise MCP tools and reject hallucinated calls. Execute + ReadOnly rejects them. Execute + Confirm/Auto/FullAccess still asks **once for every MCP call** in v1, with exact server/tool identity and bounded argument preview; server `readOnlyHint` or other annotations never grant approval. No persistent `Always` rule in v1. A denial, timeout, closed window, changed thread or cancellation is terminal and **zero network/process tool dispatch**. The local server's activation approval is separate from per-call approval.
2. Critical audit transitions commit before dispatch: proposed safe projection → approved/rejected → running → success/failed/cancelled/unknown outcome. Use the same durable call ID and owner semantics as the existing agent loop. Store a content-safe argument identity projection (server ID, config revision, exact tool name, argument byte count and digest) rather than raw secret-bearing arguments. The permission card shows this safe projection and a bounded **redacted** argument preview, never raw credential fields. A bounded tool result may enter only the existing **local** persistent conversation history so restart/context projection remains truthful; known Vega-held secret values must be filtered or rejected before card, provider projection and persistence. The UI discloses that third-party responses can still contain private data not recognizable as a Vega-held credential. Do not log raw arguments/results, Authorization headers, token responses, stderr, private paths or server-returned error text.
3. On explicit Stop, cancel the active MCP request: stdio `notifications/cancelled` and bounded child shutdown if necessary; modern Streamable HTTP closes the request-scoped response stream. A local child crash, HTTP disconnect, timeout or app restart during an approved/running call has **unknown side-effect outcome**. Mark it visibly unknown/cancelled according to actual evidence; do not auto-replay the call, even if the server reconnects. A later explicit new model/user call gets a new ID. Reconnect may refresh discovery and OAuth state but cannot silently execute an old call. Reuse a completed persisted call only after matching owner/server/config/tool/argument digest and terminal audit.
4. Third-party tool definitions, outputs and remote error bodies are prompt-injection surfaces. Label them untrusted in any historical/context-compaction projection; they cannot add system instructions, permissions, new servers, Skills or credential access. Preserve #76's model-owned context budget snapshot: all MCP tool schemas count toward input estimation on **every** provider round, including post-tool rounds. No `vega_runtime` dependency on UI/GPUI and no UI direct SQLite access.

## 8. Failure/rollback invariants

- A failed activation, auth, discovery, approval or call never falls back to a broader permission mode, different endpoint, bare shell or stale token. Current user draft and unrelated conversation remain intact.
- Disabling/deleting a server stops future authority without deleting historical audit. Rollback of code leaves additive data readable or ignored safely; never deletes credentials or history silently. A run started before a server configuration revision must not gain that revision's tools.
- External process/network side effects cannot be rolled back by Vega. Unknown-outcome calls after crash are **not idempotent** merely because JSON-RPC IDs match; no automatic replay.
